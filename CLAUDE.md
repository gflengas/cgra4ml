# Known Issues

## `quantized_model.export_graph_json()` (deepsocflow/py/brevitas/ptq.py) is not sufficient for fixed-point simulation yet

The JSON it produces (e.g. `deepsocflow/py/brevitas/model/xor_graph.json`) has enough data for the matmul/bias-add/rescale part of a fixed-point simulator, but not for the activation functions actually used, and the schema has several gaps that don't show up on the XOR model but will on anything bigger.

- **No way to execute non-piecewise-linear activations (`SiLU`, `Tanh`, `Sigmoid`, `GELU`, `SELU`) in pure integer arithmetic.** The JSON records `"activation": "silu"` plus its `bits`/`frac`/`scale`/`zero_point`, but nothing that tells a simulator how to map a quantized *input* to a quantized *output* through a curved function. `shift_round` (the round-to-nearest-even right-shift used everywhere else) only works for piecewise-linear functions through the origin like ReLU/LeakyReLU (see `quant_lrelu`, `deepsocflow/c/runtime.h:153`) - it can't compute `x * sigmoid(x)` or `tanh(x)`. The legacy qkeras backend's `_build_activation`/`XActivation` (`deepsocflow/py/xlayers.py:14-59`) confirms this was never solved even before this backend existed: it only implements `None`/`'relu'` (with power-of-two `negative_slope`) and raises `ValueError` for anything else - and `quant_lrelu` in the C firmware has no other activation path at all, so **this isn't just a JSON-schema gap, it's a real capability gap that also exists at the C/RTL deployment layer**, not something a Python-only fix can close by itself.
  - **Scoping decision (2026-08-10):** this backend's job is to port qkeras → QONNX at feature parity, not add new capability - so until the C runtime supports something better than `quant_lrelu`, only `ReLU`/`LeakyReLU` (power-of-two `negative_slope`) and `Identity` are "real" (deployable) activations. `SiLU`/`Tanh`/etc. stay supported in the *brevitas* model (fake-quantization only, via `ACT_MAP` in `ptq.py`) for QONNX export, but should not be used in models intended for eventual hardware deployment until this is resolved. `xor.py`'s `SiLU` should be swapped for `nn.LeakyReLU` (slope restricted to a negative power of two, e.g. `0.125`) to make the XOR example actually representative of what's deployable; `ptq.py` should assert the power-of-two constraint (mirroring `xlayers.py:23`) so a non-power-of-two slope fails loudly at quantization time instead of producing a model that can't be deployed.
  - **Researched design for when this gets picked up** (measured empirically against the real `xor_graph.json` fixed-point pipeline and against hls4ml's activation LUT implementations, not just theorized):
    - A pure value **LUT** (index = quantized input level → output level) is exact given its input quantization, and needs an `input_quant` added to the brevitas activation (`QuantSiLU(..., input_quant=Int8ActPerTensorFixedPoint)`) so calibration picks the table's domain/precision from real data - this input quantizer doesn't exist in the model today. hls4ml's newer `UnaryLUT`/HGQ2 path (`hls4ml/converters/keras_v3/hgq2/unary_lut.py`) does exactly this, plus a hardware trick worth reusing: it addresses the table directly by the *raw two's-complement bits* of the quantized input (table pre-permuted at export time: positive half first, negative half second) rather than by `input + 2^(bits-1)`, so no adder is needed for indexing.
    - Plain **PWL** (multiple linear segments, evaluated on the raw accumulator, no new quantization point needed) never reaches bit-exactness no matter how many segments are added (~1 LSB mismatch on 10-25% of values even at 13-21 segments) - it trades a *different*, irreducible error for not needing `input_quant`.
    - Best option found: a **"coefficient LUT"** - a small table of `(slope, intercept)` pairs indexed by the top bits of the input (via a free right-shift, no comparator chain, no search), with `slope` restricted to a sum of ≤2 signed powers of two (shift+add only, no real multiplier - keeps the same "shift-only" hardware philosophy as `quant_lrelu`/every other rescale in this project). Measured: 64 uniform segments (6-bit index) gets SiLU to 2.63% mismatch / tanh to 3.72% mismatch against the exact function, in ~128 bytes of table - beats a pure 1024-byte (10-bit) value-LUT's 4.16% mismatch on both storage and accuracy. `tanh`/`sigmoid` being odd/point-symmetric about their center lets the table (LUT or coefficient-LUT alike) be halved again by mirroring around `x=0`, `SiLU` does not have that symmetry.
    - A "range-split" idea (fine LUT only over the curved center, trivial constant/slope-1 formula for the saturated/asymptotic tails) was tried and **measured to perform worse**, not better: neither SiLU nor tanh flattens out until fairly far from the origin (`SiLU(-6) ≈ -0.015`, `tanh(2.5) ≈ 0.987`), so the "interesting" region already spans nearly the full useful input range - there's no narrow curved island to isolate, and the naive split ends up needing about as much table budget as just doing the whole range properly.
- ~~**No `signed`/`unsigned` flag per tensor.**~~ **Closed 2026-08-10** - `export_graph_json` now emits `input_signed`/`weight.signed`/`bias.signed`/`act_signed` per tensor (`ptq.py`), sourced from brevitas's own `QuantTensor.signed`/`act_quant.is_signed`. `sim.py` reads `act_signed` directly, falling back to the old name-based `UNSIGNED_ACTIVATIONS` set only for JSONs exported before this change.
- **No skip/residual-connection support in the JSON schema.** `"input"` is a single layer name or `null`; there's no `"skip_from"` the way the JSON-driven `Model._build_from_json` (`deepsocflow/py/brevitas/utils.py`) has for `residual_add`.
- **No conv/pooling hyperparameters in the export.** `export_graph_json` only ever emits `"type": "linear"` (or `"conv"` as a placeholder) - kernel_size/stride/padding for conv layers, and pooling layers entirely (`_quantize_pool`/`POOL_MAP` in `ptq.py` exist but aren't wired into `quantized_model`'s build loop or the JSON export), are not covered.
- **Rounding mode isn't recorded explicitly.** It's implicitly round-to-nearest-even (brevitas's default, confirmed via the exported QONNX `Quant` node's `rounding_mode = ROUND` attribute), but the JSON itself doesn't say so.

## `ptq.py` doesn't validate that `LeakyReLU.negative_slope` is a power of two

`quant_lrelu` (`deepsocflow/c/runtime.h:153`) computes the negative-side scaling as a pure left-shift (`x << pl_scale`), so it can only implement slopes that are exact negative powers of two (`0.5`, `0.25`, `0.125`, ...) - `xlayers.py:23` enforces this in the legacy backend with an explicit assert. `ptq.py`'s `_quantize_activation`/`ACT_MAP` maps `nn.LeakyReLU` straight to `QuantLeakyReLU` with no such check, so today it's possible to build and quantize a model with e.g. `nn.LeakyReLU(0.1)` that trains fine and calibrates fine, but silently produces a model that has no valid `quant_lrelu` parameterization and can't actually be deployed - the mismatch would only surface much later (whenever someone tries to derive `pl_scale = -log2(slope)` for the C/RTL side and gets a non-integer). Fix: add an assert in `ptq.py` (mirroring `xlayers.py:23`) that `negative_slope` is a negative power of two, so this fails loudly at quantization time instead of silently producing an undeployable model. Not yet implemented - deprioritized in favor of finishing the rest of the pipeline first.

## `xor.py`'s training is not reproducible despite `torch.manual_seed`

`train(model, ..., seed=0, ...)` (`deepsocflow/py/brevitas/xor.py`) calls `torch.manual_seed(seed)` as its first line, but by then `XOR()`'s `nn.Linear` layers have already drawn their random initial weights from the global RNG - `model = XOR()` runs *before* `train(model)` is called in `__main__`. So `manual_seed` only affects whatever nondeterminism exists inside `train()` itself (none, here - full-batch Adam is deterministic given fixed initial weights), not the actual source of run-to-run variance. Since XOR's loss landscape has dead-ReLU local optima, different unseeded initial weights sometimes converge to the correct function (`[0,1,1,0]`) and sometimes to a degenerate one (e.g. `[0,0,0,0]`) - discovered as real friction during the golden-reference-export plan (`docs/superpowers/plans/2026-08-10-brevitas-golden-reference-export.md`), where regenerating the model sometimes required 2+ retries to reach a converged state. Fix: move `torch.manual_seed(seed)` to before `model = XOR()` (or into `XOR.__init__` itself), so the seed actually controls initial weights, not just an empty stretch of RNG calls that happen to occur before them.

# Progress Log

## 2026-08-10 - float XOR model, brevitas PTQ mapping, power-of-two quantization, QONNX + graph-JSON export

- **`deepsocflow/py/brevitas/xor.py`**: rewritten from a hand-quantized (`QuantLinear`/`XBundle`) model to a plain float `nn.Module` (`Linear → SiLU → Linear → SiLU → Linear → Softmax`, all `bias=True`). Added `train()` (Adam + `NLLLoss`, early-stop `patience`), the XOR truth-table data (`X`, `Y`), and `load()`/state_dict save to `model/xor.pt`. Fixed a bug where a single shared `self.silu` attribute (used twice in `forward()`) made `net.children()`'s order not match execution order, breaking `ptq.py`'s core/activation pairing — split into `silu_1`/`silu_2`.
- **`deepsocflow/py/brevitas/ptq.py`**: new `quantized_model` class that maps an arbitrary flat float `nn.Module` onto `xbundle`/`xlayer` (not `brevitas.graph.quantize`, since that doesn't cover `LeakyReLU`/`SiLU`/`SELU`/`GELU` - this project's own `xlayer/quantActivation.py` wrappers do). Built up incrementally:
  - `LAYER_MAP`/`ACT_MAP`/`POOL_MAP` (compute layers, activations, pooling → their `xlayer` equivalents), later refactored to live as local dicts inside their respective `_quantize_*` functions instead of module-level globals.
  - `quantization(calibration_data)`: runs `brevitas.graph.calibrate.calibration_mode` so quant scales are set from real activation stats instead of brevitas's fresh-init default.
  - `export(sample_input, path)`: QONNX export via `export_qonnx(..., dynamo=False)` - `dynamo=True` (PyTorch 2.12's new default) fails on brevitas's quant proxies (`DataDependentOutputException` on `aten.allclose`).
  - Switched every quantizer from float-scale (`Int8ActPerTensorFloat`, brevitas default weight quant) to power-of-two/"fixed-point" scale (`Int8WeightPerTensorFixedPoint`, `Int8ActPerTensorFixedPoint`, `Uint8ActPerTensorFixedPoint`) - required so hardware rescale is a pure bit-shift (`shift_round`), matching this project's RTL, not a real multiply/divide. `Int32Bias` needed no change: its scale = `input_scale * weight_scale`, automatically power-of-two once both inputs are.
  - Added `bias=True` support end to end (`XOR` now trains real biases; `_quantize_layer` quantizes them via `Int32Bias`).
  - Added per-layer configurable `weight_bits`/`bias_bits` (`quantized_model(net, weight_bits=8, bias_bits=32, layer_bits={"hidden_1": {"weight_bits": 4, ...}})`), keyed by the float net's own attribute names via `net.named_children()`.
  - Added `export_graph_json(sample_input, path)`: walks `self.bundles`, writes a JSON graph (per layer: type, shape, graph topology via `"input"`, and for weight/bias/input/act - `bits`, `frac`, `scale`, `zero_point`, `values` (int level), `values_float` (dequantized)).
- **`deepsocflow/py/brevitas/xor_qonnx.py`** (new file): builds the same XOR architecture directly from `xlayer`/`xbundle` (no `quantized_model` auto-mapping), loads `xor.py`'s trained float weights via a hand-written name map, calibrates, and exports its own graph JSON - kept in sync with `ptq.py`'s fixed-point quantizer choices.
- **`deepsocflow/py/brevitas/hardware.py`** (new file): ported the legacy `Hardware` class (`deepsocflow/py/hardware.py` - `export_json`/`export`/`export_vivado_tcl`/`simulate`, config→SystemVerilog/TCL generation) into the brevitas backend. Verified the class itself has zero qkeras/TensorFlow dependency, but importing anything under `deepsocflow.*` still pulls in TF/qkeras transitively via `deepsocflow/__init__.py`'s unconditional legacy imports - noted as a blocker for ever dropping TF as a dependency (see chat; not yet fixed, since it'd require touching files the qkeras backend still uses).
- Found and fixed a real bug live: setting `bias_bits=4` in `layer_bits` silently saturated every bias value (bias `frac` is *derived* as `input_frac + weight_frac`, not independently settable - 4 bits left no integer headroom) and flipped one XOR prediction wrong; fixed by raising to `bias_bits=16`.
- Confirmed (empirically, via `onnx.load` + `IntQuantTensor.value.dtype`) that both brevitas at runtime and the exported QONNX `Quant` nodes are "fake quantization" (quantize+dequantize round-trip, computed in float32) - not real int8 execution. Real integer/fixed-point execution requires either the RTL/hardware described by `hardware.py`'s config, or a from-scratch simulator (see Known Issues above for what's still missing there).
- Investigated the SiLU/non-piecewise-linear-activation gap in depth (see Known Issues entry above for the full write-up): confirmed the C firmware's `quant_lrelu` (`deepsocflow/c/runtime.h:153`) and the legacy `XActivation` (`deepsocflow/py/xlayers.py`) only ever supported `relu`/power-of-two-slope `leaky_relu` - so this is a real capability gap at the deployment layer, not just a JSON-export gap, and `Tanh` is in the exact same unsupported position as `SiLU` (`ptq.py`'s `ACT_MAP`/`quantActivation.py`'s `QuantTanh` wrapper exist but are fake-quantization-only, same as `QuantSiLU`). Read `hls4ml`'s activation-LUT source directly (legacy `nnet_activation.h` hardcoded-range LUTs for sigmoid/tanh/elu/selu; newer `hgq2/unary_lut.py` generic `UnaryLUT` requiring an input quantizer, indexed by raw two's-complement bits) as prior art. Empirically compared LUT vs PWL vs a "coefficient-LUT" (uniform bit-indexed PWL segments, no comparator chain, shift/add-only slopes) hybrid against the real `xor_graph.json` pipeline and against synthetic SiLU/tanh sweeps - the coefficient-LUT hybrid won on both accuracy and storage size; a "range-split" (fine LUT center + trivial constant tails) hybrid was also tried and measured to be worse, since neither function's curved region is narrow enough to isolate cheaply.
- **Scoping decision:** since the assigned task is porting qkeras → QONNX, not extending capability beyond what the C runtime (`quant_lrelu`) can execute, and the user wants to stay Python-only for now (not touch `deepsocflow/c/runtime.h`), the plan is to swap `xor.py`'s `SiLU` for `nn.LeakyReLU` (power-of-two slope) to get a fully deployable pipeline working end-to-end first, and defer the SiLU/Tanh LUT/PWL work (design already researched above) until after the pipeline itself is done.

## 2026-08-10 - brevitas golden-reference (`*_exp.txt`) export, bit-exactness fixes, single quantization point

- Found and fixed two real bugs in `sim.py`'s `FixedPointModel`, discovered by comparing its per-bundle int output against brevitas's own forward pass bundle-by-bundle (not just `argmax`, which was hiding the divergence): (1) `forward()` fed one bundle's output straight into the next without requantizing when their fracs differed (every `QuantLinear` had its own `input_quant`, creating a second quantization point after each activation that qkeras never has) - fixed by requantizing (`shift_round` + clip) whenever a producing bundle's `act_frac` doesn't match the consuming bundle's `input_frac`; (2) `quantize_input` didn't clip the rounded input to `input_bits`, so `X=1.0` at `frac=7` produced `128` (one past signed int8's `127`) instead of clipping like brevitas's own input quantizer does.
- `ptq.py`: switched to a **single quantization point per bundle** - only the first bundle's `QuantLinear` gets an `input_quant`; every later bundle consumes the previous bundle's activation output directly as an already-quantized `QuantTensor` (`return_quant_tensor=True` on every activation), letting `Int32Bias` resolve its scale from that tensor directly. Also narrowed unsigned (ReLU/Sigmoid) activations to `bits-1` (mirrors the legacy `xlayers.py:31-33`'s reasoning: an unsigned 8-bit value can reach 255, which wraps if ever packed into this project's otherwise-all-signed 8-bit words). Verified empirically against the real XOR model: predictions stay `[0,1,1,0]`, and Task 3's inter-bundle requant fix becomes a structural no-op (`input_frac` now always equals the previous bundle's `act_frac`) rather than a band-aid.
- `ptq.py::export_graph_json`: added `input_signed`/`weight.signed`/`bias.signed`/`act_signed` fields, closing the "no signed/unsigned flag per tensor" Known Issue.
- `sim.py`: added per-bundle `self.trace` (`x`/`y`/`acc`/`out` per bundle, `y` being the bias-free conv-sum), softmax handling (`self.pre_softmax`/`softmax_frac`/`softmax_max_i`/`softmax_out`, mirroring the legacy `xbundle.py`'s `2**17`-factor fixed-point softmax, but normalized per-row rather than by row 0's sum - the legacy formula is only correct for `batch_size==1`), a `RuntimeError` (not a cryptic `TypeError`) when `forward()` is called before `load_int_weights()`, and defaulting bias-less layers to zero (the JSON export only emits a `"bias"` key `if quant_bias is not None` - previously unhandled since XOR always has biases).
- New `deepsocflow/py/brevitas/export.py`: `export_inference(model, hw, x_float, batch_size=1)` writes `y_exp.txt` (`%f` if the last bundle has softmax, else `%d`) and `{ib}_y_nhwc_exp.txt` per bundle into `hw.DATA_DIR` - same filenames/formats/flatten order as the legacy `deepsocflow/py/xmodel.py::export_inference`, so a future RTL step can consume them unchanged. `check_hardware(model, hw)` asserts `input_bits`/`act_bits` fit within `hw.X_BITS` and that the ACC_WIDTH bound holds, plus (post-`forward()`) that traced activation outputs fall within their signed/unsigned range - it does NOT validate weight bits against `hw.K_BITS` or bias bits against `hw.B_BITS` (a real, separately-tracked gap). Engine-layout files (`{ib}_{ip}_{it}_*`, `.bin` blobs) are deliberately deferred - see the design spec's Phase 2 (importing the legacy `dataflow.py`'s reorder functions behind a brevitas-side adapter, rather than transcribing them, since they encode non-obvious hardware invariants that only an RTL diff - out of scope this session - would catch if ported wrong).
- `main.py`: now builds `FixedPointModel` from the graph JSON, loads int weights, runs the int forward pass, and calls `export_inference` with an XOR-sized `Hardware` (`bits_input=8, bits_weights=8, bits_bias=16, bits_sum=32` - `bits_sum` needs headroom for `ACC_WIDTH = K_BITS + X_BITS + clog2(in_features)`).
- New tests: `deepsocflow/test/py/test_brevitas_sim.py` (mostly unit tests needing no training - shift_round parity vs legacy, input clipping, inter-bundle requant, per-bundle trace, softmax, error handling, signed-flag precedence - except one integration test, `test_json_has_single_quantization_point_per_bundle`, which subprocess-runs `python -m deepsocflow.py.brevitas.xor` and so retrains the model on every run; an accepted, deliberate tradeoff, not fixed) and `deepsocflow/test/py/test_brevitas_export_inference.py` (end-to-end against the checked-in trained `xor.pt`, regenerating the graph JSON into `tmp_path` every run rather than reading the repo copy).
