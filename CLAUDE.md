## `quantized_model.export_graph_json()` (deepsocflow/py/brevitas/ptq.py) is not sufficient for fixed-point simulation yet

The JSON it produces (e.g. `deepsocflow/py/brevitas/model/xor_graph.json`) has enough data for the matmul/bias-add/rescale part of a fixed-point simulator, but not for the activation functions actually used, and the schema has several gaps that don't show up on the XOR model but will on anything bigger.

- ~~**No way to execute non-piecewise-linear activations (`SiLU`, `Tanh`, `Sigmoid`, `GELU`, `SELU`) in pure integer arithmetic.**~~ **Closed 2026-08-11** - all five now run end to end as value LUTs, verified through a real RTL simulation (`Bundle 0/1, Error: 0`). See that date's "curved activations via value LUTs" Progress Log entry for the full write-up. Two things the old text here got wrong, recorded because they cost real time:
  - **It claimed the gap "also exists at the C/RTL deployment layer".** The C half was right; the **RTL half was never true**. `deepsocflow/rtl/` is a MAC array plus DMA - it has no activation logic at all (`grep -rn lrelu deepsocflow/rtl/` finds nothing), `quant_lrelu` is only ever called from `runtime.h:383/390/475`, and `create_headers` (`dataflow.py`) packs only tiling geometry into the header the fabric receives. Activation runs on the host CPU. **Adding one needs no RTL edit and no bitstream rebuild** - the existing `design_1.bit` stayed valid throughout. The project's "shift only, no multiplier" rule constrains the *RTL datapath*, which activations were never part of.
  - **The researched design below was directionally right but its headline comparison was measured against the wrong baseline.** It concluded a "coefficient LUT" (128 B, 2.63%/3.72% mismatch) beat "a pure 1024-byte (10-bit) value-LUT's 4.16%". That comparison assumed a value LUT must be indexed at 10 bits. Under variant 1b (below) a **256 B value LUT is exactly 0%**, which no PWL scheme can reach at any size - so the coefficient-LUT advantage disappears once the input quantization is what makes the table exact rather than the table's width.
- ~~**No `signed`/`unsigned` flag per tensor.**~~ **Closed 2026-08-10** - `export_graph_json` now emits `input_signed`/`weight.signed`/`bias.signed`/`act_signed` per tensor (`ptq.py`), sourced from brevitas's own `QuantTensor.signed`/`act_quant.is_signed`. `sim.py` reads `act_signed` directly, falling back to the old name-based `UNSIGNED_ACTIVATIONS` set only for JSONs exported before this change.
- **No skip/residual-connection support in the JSON schema.** `"input"` is a single layer name or `null`; there's no `"skip_from"` the way the JSON-driven `Model._build_from_json` (`deepsocflow/py/brevitas/utils.py`) has for `residual_add`.
- **No conv/pooling hyperparameters in the export.** `export_graph_json` only ever emits `"type": "linear"` (or `"conv"` as a placeholder) - kernel_size/stride/padding for conv layers, and pooling layers entirely (`_quantize_pool`/`POOL_MAP` in `ptq.py` exist but aren't wired into `quantized_model`'s build loop or the JSON export), are not covered.
- **Rounding mode isn't recorded explicitly.** It's implicitly round-to-nearest-even (brevitas's default, confirmed via the exported QONNX `Quant` node's `rounding_mode = ROUND` attribute), but the JSON itself doesn't say so.

## ~~`ptq.py` doesn't validate that `LeakyReLU.negative_slope` is a power of two~~ Closed 2026-08-11

`quant_lrelu` (`deepsocflow/c/runtime.h:153`) computes the negative-side scaling as a pure left-shift (`x << pl_scale`), so it can only implement slopes that are exact negative powers of two (`0.5`, `0.25`, `0.125`, ...) - `xlayers.py:23` enforces this in the legacy backend with an explicit assert. `ptq.py`'s `_quantize_activation`/`ACT_MAP` used to map `nn.LeakyReLU` straight to `QuantLeakyReLU` with no such check, so it was possible to build and quantize a model with e.g. `nn.LeakyReLU(0.1)` that trains fine and calibrates fine, but silently produces a model that has no valid `quant_lrelu` parameterization and can't actually be deployed - the mismatch would only surface much later (whenever someone tries to derive `pl_scale = -log2(slope)` for the C/RTL side and gets a non-integer). **Fixed**: `_quantize_activation` (`ptq.py`) now asserts `negative_slope` is a negative power of two before building `QuantLeakyReLU`, mirroring `xlayers.py:23` and `adapter.py::act_params`'s existing (later-stage) check - a non-power-of-two slope, including the `nn.LeakyReLU()` default of `0.01`, now fails loudly at quantization time with an assertion message naming the bad value, instead of silently producing an undeployable model.

## ~~`xor.py`'s training is not reproducible despite `torch.manual_seed`~~ Closed 2026-08-11

`train(model, ..., seed=0, ...)` (`deepsocflow/py/brevitas/xor.py`) used to call `torch.manual_seed(seed)` as its first line, but by then `XOR()`'s `nn.Linear` layers had already drawn their random initial weights from the global RNG - `model = XOR()` ran *before* `train(model)` was called in `__main__`. So `manual_seed` only affected whatever nondeterminism existed inside `train()` itself (none, here - full-batch Adam is deterministic given fixed initial weights), not the actual source of run-to-run variance. Since XOR's loss landscape has dead-ReLU local optima, different unseeded initial weights sometimes converged to the correct function (`[0,1,1,0]`) and sometimes to a degenerate one (e.g. `[0,0,0,0]`) - discovered as real friction during the golden-reference-export plan (`docs/superpowers/plans/2026-08-10-brevitas-golden-reference-export.md`), where regenerating the model sometimes required 2+ retries to reach a converged state.

**Fixed**: `torch.manual_seed(DEFAULT_SEED)` now runs before `model = XOR()` in both `train()`'s default argument and `__main__`, so the seed actually controls initial weights. `DEFAULT_SEED` was chosen by sweeping seeds 0-79, training each to convergence, then running each through `quantized_model` and ranking by the post-quantization softmax margin (how far the correct-class probability sits above the decision boundary on all 4 truth-table rows) - seed `30` won, converging to `[0, 1, 1, 0]` both pre- and post-quantization with a margin of ~0.9995 (max possible is 1.0). Roughly half the swept seeds landed in the dead-ReLU degenerate optimum instead, confirming the bug was real and not a rare edge case. `train()`'s `seed` parameter now defaults to `DEFAULT_SEED` instead of `0`.

This closes the practical instability too: `deepsocflow/test/py/test_brevitas_sim.py`'s `test_json_has_single_quantization_point_per_bundle` still subprocess-runs `python -m deepsocflow.py.brevitas.xor` on every `pytest` invocation (retraining is still deliberate - see the 2026-08-10 Progress Log entry), and that retrain still overwrites `model/xor.pt`/`xor.onnx`/`model/xor_graph.json` in the working tree, so those three files will still show as modified in `git status` after running the test suite. But the retrain is now deterministic and always converges to `[0, 1, 1, 0]` rather than landing on a degenerate function depending on the draw - `git checkout -- deepsocflow/py/brevitas/model/` still restores the exact committed weights if you want a clean tree.

## Verilator version: `brew install verilator` (5.050) cannot run this design; the project's pinned 5.024 cannot be built on macOS

Two independent failures, discovered while getting the brevitas XOR model through an actual RTL simulation (2026-08-11):

- **Verilator 5.050 (current `brew install verilator`) segfaults.** `deepsocflow/firebridge/fb_top_verilator_wrap.cpp` drives the simulation with a loop that calls `top->eval()`; a DPI task (`run()`, invoked from *inside* that `eval()`) itself calls back into `at_posedge_clk()` → `step_time_veri()` → `top->eval()` again - i.e. `eval()` re-enters itself. Verilator 5's scheduler does not support that re-entrancy: the initial block that calls `run()` restarts from the top on every nested `eval()` call, printing `model_setup()`'s startup banner over a thousand times before the process dies with SIGSEGV (exit 139).
- **The project's own pin, `Dockerfile:22`'s `VERILATOR_VERSION=v5.024`, will not build on this machine's toolchain (Apple clang 21).** `verilated_timing.h`'s coroutine runtime includes `<experimental/coroutine>` unconditionally on libc++, which Apple clang 21 removed; patching that guard uncovers ~14 further errors inside 5.024's own `VlCoroutineHandle`/`std::multimap` machinery that don't compile against Apple clang 21's libc++ either. Verilator itself (the tool) builds fine in isolation - it's compiling *this design* against 5.024's headers that fails.
- **The README's "Verilator 5.014+" is misleading.** The real contract is whatever `Dockerfile:22` pins (`v5.024`), which is narrower than the README states and is a Linux/libstdc++-only build in practice on this hardware generation of macOS toolchain.
- **Resolution:** run Verilator 5.024 in a Linux container instead of on the host. `deepsocflow/sim/Dockerfile.sim` builds a minimal (verilator + build-essential only, no TensorFlow/PyTorch/RISC-V toolchain) Debian image pinned to `v5.024`; on Linux/libstdc++ its coroutine runtime compiles without incident. See the 2026-08-11 Progress Log entry for how to use it.

## `Hardware`'s default `axi_width=64` silently corrupts simulation output

Discovered via A/B comparison against the working `run/xor_qkeras.py` reference (2026-08-11): building `Hardware(...)` with default `axi_width` (`64`) makes the RTL simulation *run to completion and report no error*, but bundle 0's raw engine-layout output (`{ib}_y_raw...`) has values duplicated at some offsets and dropped at others - a data-alignment corruption, not a rounding difference. `run/xor_qkeras.py` passes cleanly because it explicitly sets `axi_width=128`; setting `axi_width=128` on the brevitas XOR model's `Hardware(...)` in `deepsocflow/py/brevitas/main.py` fixes it completely. The root cause is inside the legacy AXI DMA/burst-splitting RTL and was not chased down - out of scope for the brevitas port - but this is a **live trap for anyone starting a new model from `Hardware()`'s defaults**: the default configuration produces a simulation that exits 0 and looks like it passed while silently returning wrong data. Until this is root-caused, treat `axi_width=64` as untrusted and prefer `axi_width=128` (or whatever value a known-passing reference script uses) for any new model.

## NumPy >=2.0 breaks `dataflow.py::pack_words_into_bytes` with an `OverflowError`

Discovered 2026-08-11 setting up a fresh Python 3.13 environment (`geonosis`'s `tony_cgra4ml` conda env) with no prior pin. `pack_words_into_bytes` (`deepsocflow/py/dataflow.py:282`) does `arr = arr % 2**bits` where `arr` is a `uint8` array and `2**bits` (e.g. `256` for `bits=8`) is a plain Python `int` - under NumPy's pre-2.0 promotion rules this silently computed in a wider dtype and downcast losslessly (the result is always in `[0,255]`, so mathematically a no-op), but NumPy >=2.0's stricter NEP 50 promotion casts the Python scalar to the array's own dtype *before* the operation, and `256` doesn't fit in `uint8` - raising `OverflowError: Python integer 256 out of bounds for uint8`. This is pre-existing legacy code, untouched by the 2026-08-11 TensorFlow-decoupling work (see that date's Progress Log entry) - it would fail identically on the original TF-based exporter too if ever run under NumPy 2.x, since nothing about the `.bit`-width packing math changed. Not fixed in `dataflow.py` itself (shared with the legacy qkeras backend, and the pinned fix is trivial): install `numpy==1.26.2` as `pyproject.toml` already declares, not whatever a fresh `pip`/`conda install numpy` resolves to today. A live trap for anyone setting up a new environment from scratch without pinning numpy explicitly - the failure only surfaces once `export_rtl`/`_export_bundles` actually runs (packing weights/inputs into `.bin` blobs), not at import time.

## ~~A conv layer with `CI == 1` deadlocks or silently miscomputes in the RTL~~ Worked around 2026-08-13

Found 2026-08-12, root-caused and worked around 2026-08-13. Left here in full because the symptom points nowhere near the cause, and because the workaround is a software one - the RTL defect is still there for anyone who drives the engine without going through `adapter.py`.

**Trigger: a convolution whose input has exactly one channel.** `CM_0 = 1` makes the engine's `C_CI` counter get `max_in = CM_0 - 1 = 0`, and `counter.sv` on `max_in == 0` sets `last <= 1` at load while `first = (count == max)` is also permanently 1 - the counter asserts **first and last simultaneously and forever**. `is_cin_last = l_kw && l_cin` (`axis_weight_rotator.sv:451`) is then stuck high whenever `KW == 1` too, and in `proc_engine.sv` `bypass_sum_next` (`:144`), `bypass` (`:150`) and `acc_m_valid_next` (`:376`) fire every cycle.

**Why it stops at exactly five output banks: the ceiling is `DELAY_MUL + 2`.** Confirmed by sweeping the constant rather than by reading the RTL - `DELAY_MUL=3` gives 5 banks, `DELAY_MUL=4` gives 6, while `DELAY_W_RAM` (2 -> 3 -> 4) changes nothing. `DELAY_MUL` is the depth of the `n_delay` pipeline carrying `{tvalid, tlast, tuser}` past the multiplier (`proc_engine.sv:121`). With `is_cin_last` stuck high every beat still in that pipeline claims to be a last-channel beat, so the engine drains the pipeline, emits those banks, and then has nothing left to emit. Both `DELAY_MUL` and `DELAY_W_RAM` are now real `Hardware()` parameters (`deepsocflow/py/brevitas/hardware.py`) instead of literals in the `config_hw.svh` template, which is what made the sweep possible.

Two symptoms, depending on the rest of the bundle:
- **`CI=1` + `KW=1`**: engine emits `DELAY_MUL + 2` banks and stops; the CPU spins forever on `A_DONE_WRITE`. At the hang all three DMAs report idle (`W_DONE:1 X_DONE:1 O_DONE:1`), both OCM banks are free (`DONE_READ:[1,1]`) and `o_valid` is low - not back pressure. Invariant across XW, row-block split, AXI width (64 and 128), PE geometry (8x24, 7x24, 7x96), `max_kernel_size` and `bits_input`.
- **`CI=1` + `KH>1` + batch > 1**: runs to completion and produces **wrong values**.

**Measured boundary: `CI=1` fails, `CI=2` onward is fine.**

**Why nothing ever hit it:** `run/resnet50.py` takes RGB input (`CI=3`) and its 36 1x1 convs all sit at `CI >= 64`; `run/example.py` has `CI=1` in bundle 1 (grayscale MNIST) but runs at `batch_size=1` with `KH=KW=7`, the one `CI=1` combination that survives; the XOR model is dense-only, where `export_bundle` folds the batch into the height axis so `XW=1` and one bank per bundle. Note `resnet50.py` uses `bits_input=8`, same as the brevitas backend - bit width is **not** the discriminator despite being the obvious suspect.

**Workaround (implemented): `adapter.py::pad_single_input_channel` pads a one-channel layer to two with zeros.** The added channel contributes zero to every accumulation, so not one output value changes; only what the engine is *told* about the layer changes, and `CM_0` becomes 2. Costs one extra input channel on the first layer, needs no RTL change, and leaves the existing bitstream valid. Applies to dense (`in_features == 1`) as well, which is the same degenerate case. Verified on all three failing shapes: `KW=1/CI=1/XW=16` now emits all 16 banks, `KW=3/CI=1/batch=4` all 28, both `Error: 0`. `deepsocflow/py/brevitas/conv.py` deliberately keeps its synthetic images grayscale so every bring-up stage exercises this path.

**The RTL defect itself is not fixed.** A real fix means making `proc_engine.sv`'s accumulator pipeline handle a 1-tap accumulation, which needs re-synthesis and a new bitstream - something the whole brevitas port has avoided needing. The counter is arguably correct (a length-1 loop *is* both first and last). Anyone driving the engine without `adapter.py` in the path still has to avoid `CI == 1`.

**Diagnostic tooling added while finding it:** the `while (!fb_read_reg32(... A_DONE_WRITE ...))` spin in `deepsocflow/c/runtime.h` now bails out after 5000 iterations under `#ifdef SIM` and prints `A_W_DONE`/`A_X_DONE`/`A_O_DONE`/`DONE_READ`/`DONE_WRITE`/`A_BUNDLE_DONE` - the registers whose declarations already say "written by PL, read by PS to debug which one hangs". That turned "it hangs" into "which DMA is idle" in one run, after several rounds of blind config bisection had produced nothing. Keep it.

## 2026-08-10 - brevitas golden-reference (`*_exp.txt`) export, bit-exactness fixes, single quantization point

- Found and fixed two real bugs in `sim.py`'s `FixedPointModel`, discovered by comparing its per-bundle int output against brevitas's own forward pass bundle-by-bundle (not just `argmax`, which was hiding the divergence): (1) `forward()` fed one bundle's output straight into the next without requantizing when their fracs differed (every `QuantLinear` had its own `input_quant`, creating a second quantization point after each activation that qkeras never has) - fixed by requantizing (`shift_round` + clip) whenever a producing bundle's `act_frac` doesn't match the consuming bundle's `input_frac`; (2) `quantize_input` didn't clip the rounded input to `input_bits`, so `X=1.0` at `frac=7` produced `128` (one past signed int8's `127`) instead of clipping like brevitas's own input quantizer does.
- `ptq.py`: switched to a **single quantization point per bundle** - only the first bundle's `QuantLinear` gets an `input_quant`; every later bundle consumes the previous bundle's activation output directly as an already-quantized `QuantTensor` (`return_quant_tensor=True` on every activation), letting `Int32Bias` resolve its scale from that tensor directly. Also narrowed unsigned (ReLU/Sigmoid) activations to `bits-1` (mirrors the legacy `xlayers.py:31-33`'s reasoning: an unsigned 8-bit value can reach 255, which wraps if ever packed into this project's otherwise-all-signed 8-bit words). Verified empirically against the real XOR model: predictions stay `[0,1,1,0]`, and Task 3's inter-bundle requant fix becomes a structural no-op (`input_frac` now always equals the previous bundle's `act_frac`) rather than a band-aid.
- `ptq.py::export_graph_json`: added `input_signed`/`weight.signed`/`bias.signed`/`act_signed` fields, closing the "no signed/unsigned flag per tensor" Known Issue.

## 2026-08-11 - brevitas → RTL end-to-end: adapter onto the legacy engine-layout exporter, RTL simulation passes on XOR

**Result: RTL simulation now passes for the brevitas XOR model, verified against the same Python fixed-point golden reference `sim.py`/`export.py` already produced.** `docs/superpowers/plans/2026-08-11-brevitas-rtl-end-to-end.md` / `.superpowers/sdd/2026-08-11-brevitas-rtl-end-to-end/progress.md` has the full nine-task ledger; this entry is the durable summary.

- **The adapter approach, and why.** The 2026-08-10 work (see above) got as far as a golden reference (`export.py::export_inference`) - flat `*_exp.txt` files nothing downstream reads yet. RTL actually consumes a different, denser file set: per-bundle engine-layout text/`.bin` blobs plus `config_fw.h`, produced by the legacy qkeras backend's `deepsocflow/py/xmodel.py` (`_export_bundles`) walking `XBundle`/`XDense`/`XActivation` objects (`deepsocflow/py/xbundle.py`, `deepsocflow/py/xlayers.py`). Two ways to get there were on the table: re-derive that file format independently in the brevitas backend, or reuse the legacy backend's own exporter by making brevitas's numbers look like an `XBundle` to it. **Reuse won** - the file format encodes non-obvious hardware invariants (bit-packing order, per-pass channel slicing, bias shift derivations) that only an RTL diff would catch if transcribed wrong, and the legacy code already carries that RTL-verified knowledge. The result is `deepsocflow/py/brevitas/adapter.py`: `BrevitasBundle`/`_Core`/`_Act` wear exactly the attribute surface `XBundle.export` (`xbundle.py`) and `config_fw.h`'s writer (`xmodel.py:234`) read, populated directly from `FixedPointModel.trace` (brevitas's own already-computed integer tensors) rather than recomputed - `BrevitasBundle.call_int` is a deliberate no-op, since re-deriving the bundle in integer arithmetic here would either duplicate `sim.py` or silently disagree with it. The module docstring states the split plainly: "brevitas owns the numbers; the legacy backend owns the file format." `export.py::export_rtl(model, hw, x_float, batch_size)` is the new entry point that drives it, calling `adapter.build_bundles()` then the legacy `xmodel.py::_export_bundles`.
- **`xmodel.py` preamble/bundle-loop split (commit `b52834c`, prerequisite refactor).** `export_inference` used to do keras-specific setup (clearing `hw.DATA_DIR`, printing "STARTING EXPORT") and the bundle-walking loop in one function. Split into a keras-only preamble (left in `export_inference`) and a keras-agnostic `_export_bundles(hw, x)` that only touches the `BUNDLES` global and `hw` - a pure move (+7 lines, no re-indentation, both were already module-level), verified byte-identical against the pre-split body. This is what lets the brevitas adapter call `_export_bundles` directly without dragging in any keras/TensorFlow import.
- **The qkeras XOR baseline (`run/xor_qkeras.py`) served two roles throughout:** (1) reference for what a passing RTL run looks like at all (used to A/B the axi_width=64 corruption below, and to confirm the Verilator-version diagnosis before touching this branch's own code), and (2) a standing regression - re-run after nearly every task to confirm nothing in the shared legacy path (`xbundle.py`, `xmodel.py`, `dataflow.py`) broke. It caught a real regression: commit `d3091e2` ("brevitas layers added") had deleted `ic_right += CM_p` from `XBundle.export`'s per-pass loop while adding comments, leaving `ic_left`/`ic_right` both stuck at 0 so every pass sliced input channels `[0:0]` (`filter depth must be strictly positive, got 0`). This is a pre-existing-code regression, not something introduced by the brevitas port, and it broke the qkeras path too (`run/example.py`). Fixed by restoring the increment as an extracted `_pass_channel_slices(r)` helper plus 4 unit tests (commit `65e50b2`); the qkeras baseline (`run/example.py`, all 7 bundles) and `run/xor_qkeras.py` both pass RTL sim again.
- **The four-row export.** `export_rtl`'s `batch_size` defaults to `4` (all four XOR truth-table rows), not `1` like `export_inference`'s golden-reference `batch_size` convention - the RTL testbench is driven once per invocation and needs the whole truth table in a single pass to be a meaningful hardware-level check, whereas the Python-only golden reference only ever needed to prove per-row bit-exactness.
- **Adapter defects, all one family.** Legacy `XBundle` populates several attributes (`bias_val_shift`/`bias_b_shift`, `softmax_frac`/`softmax_max_i`, `is_flatten`/`is_softmax`) inside `call_int`, which the adapter deliberately never runs - so each had to be supplied explicitly, and each was missed at least once before `_export_bundles` was actually exercised end to end: (1) `bias_val_shift`/`bias_b_shift` missing entirely (`config_fw.h`'s writer reads them at `xmodel.py:234`) - fixed by setting both to `0`, provably so rather than by assumption: `add_val_shift` (`utils.py:66-81`) returns `(max(y.frac,b.frac)-y.frac, max(y.frac,b.frac)-b.frac)`, and brevitas's single-quantization-point-per-bundle design makes `bias_frac == acc_frac` always (`sim.py:166` asserts it outright), so both differences are identically zero. (2) `softmax_frac`/`softmax_max_i` missing, defaulted per `xbundle.py:47-48`, real values read off `sim.py:190,194`. (3) `is_flatten`/`is_softmax` stored as `False` instead of `None` when absent - `xmodel.py:233` emits them with `is not None`, while legacy itself stores `None` (`xbundle.py:41,44`) and tests truthiness elsewhere (`xbundle.py:144`, `xmodel.py:221`); `False` satisfies neither convention and made every bundle claim to be both flattened and softmaxed. **The lesson that stopped the bleeding:** none of these were catchable by testing the adapter's own attributes or even `.export()` in isolation - they only became visible once a test drove the *real* `_export_bundles` path and asserted on the emitted `config_fw.h` text, the level each bug was actually visible at (`test_full_legacy_export_path_runs_on_adapted_bundles`, `test_legacy_xbundle_export_runs_on_adapted_bundles`). Anyone extending the adapter for a new layer type should assume the same failure mode: any attribute normally set inside `call_int` needs to be supplied explicitly and verified against a real `config_fw.h` dump, not inferred from the dataclass shape.
- **Two environment traps, now load-bearing enough to also live as their own Known Issues above:** the Verilator version pin (`brew`'s 5.050 segfaults on this design's re-entrant `eval()`; the project's pinned `v5.024` cannot be built against Apple clang 21's libc++; resolved by running `v5.024` inside a Debian container) and `Hardware`'s default `axi_width=64` silently corrupting bundle-0 output (fixed by `axi_width=128`, matching `run/xor_qkeras.py`).

Any script run as `cd run && python ...` silently executes that other copy instead of this worktree's code - Task 1.5 initially "passed" against the wrong code this way. Always run from the worktree root (cwd wins over the `.pth` entry on `sys.path`), or use `deepsocflow/sim/docker_sim.py`, which inserts the worktree root at `sys.path[0]` itself.

These were working-session scratch files outside the repo during this task; without moving them, the only way to run a simulation on this machine would need to be rediscovered from scratch next time. `docker_sim.py` monkeypatches `deepsocflow.py.hardware.Hardware.simulate` (the **legacy** `Hardware` class - the brevitas backend's own `deepsocflow/py/brevitas/hardware.py::Hardware` is a separate, non-inheriting class kept deliberately free of the TensorFlow/qkeras import chain) to shell out to `run-sim-in-docker.sh` instead of invoking a local `verilator`/`xsim` binary. ## 2026-08-11 - curved activations via value LUTs: SiLU/Tanh/Sigmoid/GELU/SELU deployable, RTL sim passes bit-exactly

**Result: the five curved activations now run end to end - brevitas → `sim.py` → `config_fw.h` → `runtime.h` → RTL - with `Bundle 0, Error: 0` / `Bundle 1, Error: 0` on a SiLU XOR model.** This closes the oldest Known Issue in this file (see the corrections recorded there). Branch `brevitas-lut-activation`; design in `docs/superpowers/specs/2026-08-11-lut-activation-design.md`, task ledger in `docs/superpowers/plans/2026-08-11-lut-activation.md`. 116 tests passing (baseline 41).

- **The finding the whole thing rests on: activation is computed on the host CPU, not in RTL.** Verified three ways (no activation logic under `deepsocflow/rtl/`; `quant_lrelu` called only from `runtime.h:383/390/475`; `create_headers` packs only tiling geometry into the fabric's header). So this was a firmware change, not a hardware one - **no RTL edit, no re-synthesis, no bitstream rebuild**. The existing `design_1.bit` stayed valid the entire time. Anyone extending activations further should start here rather than assuming the fabric is involved.
- **Variant 1a vs 1b - they are not two table layouts, they are two definitions of "exact".** A 1a and a 1b table on the same grid are *byte-identical*, and the firmware is the same three steps (`shift_round` → `clip` → table load) either way. What differs is what brevitas computes: 1a evaluates the activation on the full-precision accumulator, 1b quantizes the accumulator first (via an `input_quant` on the activation, `ptq.py`'s new `act_input_bits`).
  - **1a is not a cheaper-but-acceptable option - it is wrong.** Measured against brevitas's own activation output (captured by forward hook on `core.act`, not a reconstructed reference), on trained XOR models: SiLU 29.7% of values differ (worst 8 LSB), GELU 12.5%, SELU 21.9%, Tanh 76.6% (worst 31 LSB), **Sigmoid 100.0% (worst 71 LSB) - and its prediction comes out wrong**. Earlier 1a runs all still predicted XOR correctly, which made it look merely imprecise; sigmoid is the case that shows it can break the model.
  - **1a can be made bit-exact, but only by indexing at the accumulator's own frac** - measured law, holds for all five: exact iff `in_frac == acc_frac` and `in_bits` covers the real accumulator range. That costs **64-128 KB per activation** (17-bit index at `acc_frac=13`), vs 1b's 256 B.
  - **1b is bit-exact at every input width tried - 4, 5, 6, 7, 8, 10 bits** (16 B to 2 KB tables), for all five activations. Exactness comes from the table sharing brevitas's grid, not from that grid being fine.
- **The invariant scare was unfounded, and this was measured rather than assumed.** An earlier read of 1b was that it breaks the 2026-08-10 "single quantization point per bundle" design. It does not: the real invariant is `act_frac[N] == input_frac[N+1]` (the seam *between* bundles), which holds on both 1a and 1b models, as does `acc_frac == bias_frac` (`sim.py:169`). `input_quant` sits *inside* a bundle, between accumulator and activation - the place the pipeline already shifts. Runtime cost vs 1a is zero; vs `quant_lrelu` it is one table load.
- **The one attribute whose *meaning* changes: `_Act.shift_bits`.** On the `quant_lrelu` path it is the shift onto the activation's **output** grid; on a LUT bundle it is the shift onto the **table's index** grid (`acc_frac - act_in_frac`), because the table itself produces the output grid. These coincide only under 1a, so using `act_frac` here yields a model that runs, looks plausible, and is silently wrong on every 1b model. Same family as the four `call_int`-derived adapter defects the 2026-08-11 RTL entry lists.
- **A C-level trap worth keeping:** `Bundle_t` gained `ca_lut_idx`/`ca_lut_bits`, but the legacy qkeras exporter (`xmodel.py`) does not emit them - and C designated initializers default missing fields to **0**, which would read as "use table 0". What makes that safe is that the same exporter also emits no `N_LUTS`, so `#if defined(N_LUTS) && N_LUTS > 0` compiles the lookup out entirely. **Keep that guard if you touch the dispatch.** Verified by compiling both configurations and by a standalone C unit test of `quant_lut` (all 16 levels of a 4-bit table plus saturation at both edges).
- **Table sharing is keyed on contents, not on the activation's name.** Two bundles both using SiLU do *not* share a table, because calibration gives each its own scale. Storage therefore scales with the number of curved bundles, not the number of distinct activation types - relevant if a larger network ever makes `LUT_ENTRIES` padding expensive.
- **Regression evidence, since this touched the shared `runtime.h`:** the qkeras baselines still pass with `Error: 0` on every non-softmax bundle - `run/xor_qkeras.py` (3 bundles) and `run/example.py` (**all 7 bundles**, exercising conv/pool/residual, which nothing brevitas-driven covers). Separately, a byte-diff of the existing LeakyReLU XOR export before/after showed 23 of 25 files byte-identical, with `config_fw.h`/`config.json` differing *only* by the added fields (`N_LUTS 0`, `ca_lut_idx=-1`, `luts: []`) and no existing value changed.

### Still open

- ~~**What `act_input_bits` should actually be.**~~ **Answered 2026-08-11 - use 10, or 8 if table space is tight; never below 8.** See the "regression benchmark" subsection below.
  - **`act_input_bits` is NOT constrained by the hardware's activation width, and the two are easy to conflate.** `X_BITS` (8 here) is how wide an activation *word in memory* is - it bounds the table's *entries*. The table's *index* is computed in an i32 register on the CPU, used once to address the table, and thrown away; it never becomes a stored value. So 8-bit activations run a 10- or 12-bit index perfectly well - the table just gets more rows, each still one byte. `check_hardware` enforces exactly that asymmetry (`out_bits <= hw.X_BITS`; `in_bits` bounded only by table size). **Verified end to end:** the 4-hidden-layer SiLU model with `act_input_bits=10` on `bits_input=8` hardware exports `X_BITS_L2=3` (X_BITS=8) with `LUT_ENTRIES 1024`, table values in `[-4, 127]`, `.bin` blobs still 8-bit packed, and passes RTL simulation with `Bundle 0-4, Error: 0`. The only real cost of a wider index is table storage: 4x per extra 2 bits (1 KB -> 4 KB total for that 4-bundle model).
- **Residual-add (`aa_*`) and pool (`pa_*`) activation slots are untouched** - the brevitas adapter supports neither, so LUT code there would be untested speculation. Same reasoning as the `adapter.py` Part B defects recorded above.

- **10 bits is where accuracy converges** (12 buys ~0.01-0.04 dB more). 8 bits costs ~0.4-0.6 dB over the converged value. **Below 8 the model degrades fast, and below ~6 it degrades erratically rather than smoothly** - SiLU at 4 bits (8.75) scored *better* than at 5 bits (10.17), i.e. calibration is no longer finding a sensible scale at all. Do not read "bit-exact at 4 bits" as "4 bits is usable"; those are independent axes and only the first is what 1b guarantees.
- **The `hw-model` column is the argument for 1b in one number.** Under 1b it is exactly 0.0000 at every width: the hardware computes precisely what the quantized model predicts, so the model's own accuracy figure is trustworthy. Under 1a the hardware is *worse than the model claims* - by +0.15 dB for SiLU and **+1.86 dB for Tanh, a 74% RMSE inflation the model has no way to report**. 1a does not merely lose bit-exactness; it makes the model's accuracy number a lie.
- **Depth makes 1a worse, and 1b indifferent.** Going from 2 to 4 hidden layers pushed 1a's Tanh gap from +1.15 to +1.86 dB and its mismatch from 70.3% to 78.8% (error compounds through successive activations), while 1b stayed at exactly 0.0000 throughout.
### Classification benchmark - and a real bug it caught

`deepsocflow/py/brevitas/lut_classification_bench.py` (new; UCI Letter Recognition, 20000x16 -> 26 classes, gitignored). Regression measures error proportionally; a classifier hides it behind an argmax until one flips. The metric that matters here is therefore **flips** - inputs where the hardware picks a *different class* than the quantized model said it would - not accuracy, because flips can cancel and leave accuracy looking fine.

16 -> 64 -> 64 -> 64 -> 26, 4000 held-out samples, float32 accuracy 95.50% (SiLU) / 95.38% (Tanh):

| config | model acc | hw acc | **flips** | vs brevitas | bytes |
|---|---|---|---|---|---|
| 1a | 95.00 / 95.43 | 94.60 / 94.53 | **1.90% / 2.53%** | 24.8% / 81.9% | 768 |
| 1b @ 4b | 67.40 / 79.30 | same | **0%** | 0% | 48 |
| 1b @ 6b | 93.15 / 94.80 | same | **0%** | 0% | 192 |
| 1b @ 8b | 94.60 / 95.40 | same | **0%** | 0% | 768 |
| 1b @ 10b | 95.12 / 95.38 | same | **0%** | 0% | 3072 |

**Under 1a the hardware answers a different class than the model predicts on ~2-2.5% of inputs** while accuracy only moves 0.4-0.9pp - i.e. the accuracy figure alone would have hidden it. Under 1b, flips are exactly zero at every width. Same conclusion as the regression benchmark (10 bits converges, 8 is the floor, below 6 collapses - here to 67% accuracy).

**The bug this benchmark caught: the table was being built in float64, but brevitas evaluates activations in float32.** At 10- and 12-bit tables it showed 0.20%/0.05% disagreement against brevitas - small, but this design's entire value is that the number is *zero*. Root cause: `silu(24.75)` is `24.75` exactly in float32 but `24.749999999558646` in float64; at `out_frac=1` those round to `50` and `49`. **Building the table in float64 makes it more mathematically accurate and less faithful to the model it has to reproduce** - and only for inputs large enough for the deviation to cross a rounding boundary, which is why neither XOR nor the standardised regression target ever surfaced it (their activations stay small). Fixed in `lut.py` by computing both the table and `exact_activation` in float32; pinned by `test_table_is_built_in_float32_like_brevitas` and a parametrised large-input check over all five activations. **Anyone adding another reference implementation of an activation - the PYNQ driver, a future C-side table generator - has to match brevitas's precision, not exceed it.**

- **The deep model also passes RTL simulation**, and more convincingly than XOR did: `Bundle 0/1/2/3, Error: 0` on the four SiLU bundles plus `Bundle 4, Error: 0.0` on the output. Because this model has no softmax, that last bundle is a genuine integer comparison - unlike XOR's final bundle, whose `atol=0.5`-against-probabilities check cannot fail and proves nothing. 47 s under xsim.

## 2026-08-12 - Conv2d on the brevitas backend: conv/stride/pool/flatten end to end, bit-exact under RTL

**Result: a 5-bundle CNN (conv -> conv -> maxpool -> 1x1 conv -> flatten -> dense -> softmax) runs the full brevitas -> `sim.py` -> `config_fw.h` -> `runtime.h` -> RTL path with `Bundle 0/1/2, Error: 0` and predictions matching brevitas exactly.** Before this the brevitas backend was dense-only; conv/pool/residual were exercised solely by the pre-existing qkeras `run/example.py`.

- **The legacy side already did all the hard parts, and reusing it was the whole strategy.** `dataflow.py::get_runtime_params` handles conv striding, `'same'` padding shifts and pooling geometry; `rtl_export.py::export_bundle` has a conv branch and `_conv2d_same`; `runtime.h` implements conv striding, pooling and flatten on the CPU. All of it is numpy-only since the 2026-08-11 TensorFlow decoupling. **No RTL edit, no bitstream rebuild** - same property the LUT work had. What was missing was entirely brevitas-side: `ptq.py` never emitted conv geometry, `sim.py::forward` was `inp @ weight.T`, and `adapter.py::_Core` hardcoded `type='dense'`.
- **Brought up in five stages, each adding exactly one thing** (`conv.py`'s `StageA`..`StageE`, driven by `conv_main.py --stage`): 1x1 conv (layout plumbing only), 3x3 `'same'` (real conv math), stride 2, MaxPool, then flatten -> dense -> softmax. Every stage ends in a real RTL run, not a unit test - the 2026-08-11 adapter work established that this class of bug only appears once `_export_bundles` is actually driven, and that held again here.
- **Two layout conventions differ between torch and the engine, and both fail silently** - same shapes, plausible numbers, everything shifted:
  - **Strided conv anchors differently.** The engine follows TF `'same'`, padding `max((ceil(n/s)-1)*s + k - n, 0)` with the smaller half on top/left, so a 3x3 stride-2 conv over an 8-wide axis starts at row **1**. torch's `Conv2d` cannot express asymmetric padding through `padding=`, so the natural spelling pads (1,1) and starts at row **0**. Measured as 87/128 values differing. The two coincide when TF's total padding equals `k-1`, which for k=3/s=2 means an **odd** input size - hence stage c uses 7x7 rather than 8x8. `ptq.py::_assert_stride_matches_engine` now refuses the mismatching case at quantization time and names the sizes.
  - **Flatten orders differently.** `nn.Flatten` over NCHW gives C,H,W (W fastest); `runtime.h`'s `tile_write` gives `i_yc = (i_yh*yw + i_yw)*yc + i_yc`, i.e. H,W,C (C fastest). Handled by permuting the consuming dense layer's weight columns (`sim.py::nchw_to_nhwc_flatten_perm`). Critically, `forward()` publishes the permuted matrix as `bundle['weight_engine']` and `adapter.py` exports *that* - deriving the permutation twice is exactly how the engine ends up multiplying by a differently-ordered matrix than the reference, and the first attempt did precisely that (`Bundle 3` mismatched while bundles 0-2 were exact).
- **`Hardware()` defaults that are fine for XOR are not fine for conv.** `valid_prob`/`ready_prob` default to `0.01`/`0.1`, randomly throttling the AXI-Stream handshakes - survivable for XOR's 4 pixels, but it makes an 8x8 image look like a hung simulation. `ram_edges_depth=288` is too small once `KH>1` at this width. `conv_main.py` copies `run/example.py`'s values (`1`/`1`, `3584`) and says why at the constructor.
- **`_quantize_pool` was dead code and wrong**: it called `quant_cls()` with no arguments, dropping kernel_size/stride/padding entirely. Now forwards them, attaches the `type`/`pool_layer` surface `dataflow.py` reads, and gives the pool an `nn.Identity` act (max pooling returns a value already on the activation's grid, so there is genuinely nothing to rescale). **Max only** - average pooling would have to reproduce `runtime.h`'s `div_round` and widened accumulator bit-for-bit while brevitas's `TruncAvgPool2d` truncates on a different rule.
- **Found a real RTL bug on the way: `CI == 1` deadlocks or miscomputes.** Root-caused and worked around the next day - see the Known Issue above. It cost most of this session, and the symptom points nowhere near the cause.
- **Verification:** `pytest deepsocflow/test/py/ -q` -> **140 passed, 4 skipped** (123 baseline + 17 new in `test_brevitas_conv.py`; the load-bearing one asserts `sim.py::conv2d_same_int` and `rtl_export.py::_conv2d_same` agree, since every "Error: 0" in this backend rests on those two independent implementations matching). All five stages pass under xsim at batch 4. The XOR/dense/LUT path still passes unchanged (`[0,1,1,0]`, `Bundle 0/1, Error: 0`). One pre-existing test was updated rather than fixed: `test_unsupported_layer_type_raises` asserted `type='conv'` raises, which is the behaviour this work deliberately removed.
- **Not covered:** residual/skip (the `next_add_ibs` set-vs-list defect above is still the first thing to fix there), average pooling, `CI=1`, and real hardware - everything here is Python + C + RTL simulation. `run/example.py`/`run/xor_qkeras.py` could **not** be run as regression on this machine (no TensorFlow under Python 3.13), so the claim that the shared legacy path is unaffected rests on the brevitas-side suites plus the unchanged XOR run, not on the qkeras baselines.

## 2026-08-13 - `CI == 1` root-caused (`DELAY_MUL + 2`) and worked around by zero-padding

Follow-up to the previous day's conv bring-up, which had left `CI == 1` recorded but unexplained and unfixed. Both are now closed; the full write-up lives in the Known Issue above, this entry records how it was found and what it cost.

- **The "why exactly five banks" question was answered by sweeping a constant, not by reading RTL.** `DELAY_MUL` and `DELAY_W_RAM` were literals in `hardware.py`'s `config_hw.svh` template, marked "constant, for now"; making them real `Hardware()` parameters took one edit and turned an unanswerable question into a three-run experiment. `DELAY_MUL=3 -> 5` banks, `DELAY_MUL=4 -> 6`, `DELAY_W_RAM` irrelevant. **Reach for parameterising a hardcoded constant earlier than feels justified** - the previous day was spent bisecting the wrong axis (AXI width, PE geometry, `max_kernel_size`, bit widths) precisely because the interesting constants were not adjustable.
- **The fix is a zero-pad, not an RTL change.** `adapter.py::pad_single_input_channel` widens a one-channel layer to two. Zeros contribute nothing to any accumulation, so no output value moves - what changes is only what the engine is told, which is enough to make `CM_0 == 2` and the `C_CI` counter well behaved. Same shape of decision as everything else in this port: software-only, existing bitstream stays valid.
- **The synthetic dataset was moved BACK to grayscale (`conv.py`'s `CHANNELS = 1`).** It had been widened to 3 channels the day before purely to dodge the bug. Now that the pad exists, keeping the images single-channel means every bring-up stage runs through the workaround on every invocation, while each model's second layer (`CI` 4 or 8) still covers the ordinary path. A workaround nothing exercises is a workaround that rots.
- **Verification:** `pytest deepsocflow/test/py/ -q` -> **142 passed, 4 skipped** (two new tests pin that the pad is numerically exact and that it leaves normal layers untouched - the failure mode worth guarding is a pad that changes values, which would swap a loud bug for a quiet one). All five conv stages pass under xsim at batch 4 on grayscale input: `Bundle 0/1, Error: 0` for a-d, `Bundle 0/1/2, Error: 0` for e. XOR/dense/LUT unchanged (`[0,1,1,0]`, `Bundle 0/1, Error: 0`).
- **Still open:** the RTL defect itself, residual/skip, average pooling, and real hardware. `run/example.py`/`run/xor_qkeras.py` still cannot be run here as regression (no TensorFlow under Python 3.13).

## 2026-08-13 - residual add and average pooling: a ResNet-shaped bundle graph runs bit-exact

Closes the last two capabilities the brevitas backend was missing relative to what the RTL can execute. Design survey: `docs/superpowers/specs/2026-08-13-residual-and-avgpool-design.md`. Seven bring-up stages now pass under xsim (`conv_main.py --stage a..g`), 146 tests.

- **Most of both features already existed and just was not wired up.** `runtime.h`'s residual add, `rtl_export.py`'s add-buffer allocator, `XBundle.call(x, x_add)`, `QuantResidualAdd`, and `XTensor.add_val_shift` were all complete. What was missing was entirely on the brevitas side. Survey before building: the first version of this plan proposed re-deriving several things that were already there.
- **The constraint that shapes residual: hardware does not align the addends.** `Bundle_t` has `b_val_shift`/`b_bias_shift` for the bias and `aa_*` for the add activation, but **no `add_val_shift`/`add_a_shift`** - the C does a bare `out_val += mp->add_buffers[...]` (`runtime.h:451`). Legacy's `XAdd.call_int` computes alignment shifts that **nothing ever transports to the firmware**. Meanwhile the Python side would happily align them (`add_val_shift` shifts both onto `max(frac)`). So the two agree only when the fracs already match, and a mismatch is wrong by a power of two while looking entirely plausible - it also corrupts `aa_shift`, which is derived from the summed frac. Handled two ways: `ptq.py`'s new `residuals={consumer: source}` shares the source's **act quant proxy** with the consumer (`QuantReLU(act_quant=other.act_quant)`, via brevitas's `add_tracked_module`), and `check_hardware` asserts frac equality naming both bundles. Sharing the proxy does **not** break the single-quantization-point-per-bundle invariant - each bundle still has one act-quant step, they just consult one scale - but it does share the *nonlinearity* too (the proxy owns `act_impl`), so both ends must be the same activation type; asserted.
- **Topology is declared, not traced.** `quantized_model` walks `net.named_children()` linearly and its `forward` had no `x_add` at all. `torch.fx` is not an option (brevitas's quant proxies break dynamo - already documented at `export()`), so skips are declared as `{consumer_attr: source_attr}` and `forward` keeps per-bundle outputs. Everything downstream reads the JSON, so real tracing can replace this later without touching anything else. **Reusing one activation *module* across two bundles is not a workaround** - `named_children()` dedupes by identity, so the second bundle would silently consume the wrong child and shift the whole layer/activation pairing.
- **`next_add_ibs` had to become an ordered list.** `rtl_export.py:205` frees an add buffer when `buf['out'][-1] == b.ib`, i.e. it reads the last consumer by index; the adapter used a `set`. One bundle feeding several consumers is the normal residual shape, so an unordered collection frees the buffer at the first consumer and the rest read memory that has been reused. Fixed in the adapter (list, appended in ib order) *and* defensively in the exporter (`sorted()`, mirroring what `next_ibs` already did).
- **`div_round` is not rounding, and that had to be measured.** Average pooling's whole bit-exactness claim is that `runtime.h`'s `div_round` macro is reproduced. It deviates from round-half-away-from-zero on **13271 of 29080** swept inputs - always by at most 1, almost always on negatives: `div_round(-4, 4)` is `0`, not `-1`. It is now pinned against the **compiled C macro** (`deepsocflow/test/c/div_round_dump.c` dumps a table; `test_div_round_matches_c` asserts against it), the same technique the LUT work used for `quant_lut`. A Python transcription checked only by reading would have looked like a plausible rounding choice either way.
- **That same sweep retired a `runtime.h` bug without fixing it.** `runtime.h:534-538` applies the avg-pool activation to `out_val` (the *pre-pool* pixel) and then writes `result`, so `pa_*` has no effect and the pooled value is never clipped to `X_BITS`. The sweep shows **0 of 29080 results fall outside `[-128,127]`** - an average of in-range values is in range - so the missing clip can never fire while the pool activation is the identity. Recorded, guarded (`ptq.py` refuses an activation after a pool, which would otherwise be silently dropped - for max pooling `pa_*` is never applied at all), and deliberately **not** fixed: the cost of touching `runtime.h` is that `run/work_pynq/pynq_deploy/pynq_driver.py` mirrors it in Python and must follow.
- **brevitas's `QuantAvgPool2d` is the wrong operation.** It is `TruncAvgPool2d`, which sums and *truncates to a bit width* - a shift, not a divide-and-round. New `xlayer/quantAvgPoolDivRound.py` computes what the engine computes, on the integer grid, so the float model and the hardware agree exactly. Same principle as the LUT work: make the model reproduce the hardware rather than hope a library's approximation is close enough. One wrinkle worth knowing - brevitas's `calibration_mode` disables the upstream activation's quantizer while collecting statistics, so the pool receives a **plain tensor** on that pass and falls back to an ordinary mean; every real inference pass takes the integer path.
- **Verification:** all seven stages under xsim at batch 4 - `Bundle n, Error: 0` throughout, and `sim.py` vs brevitas differs by **exactly 0 values** on every stage except `e`, whose softmax output is float32-vs-float64 noise (`2.98e-08`, 0 prediction flips). `pytest` 146 passed / 4 skipped. XOR/dense/LUT unchanged. Nothing under `dataflow.py`, `runtime.h`, `rtl/` or `pynq_driver.py` was touched.
- **Still open:** average pooling with `'same'` padding (the engine's divisor shrinks at the borders), `torch.fx` topology inference, the `CI == 1` RTL defect itself (worked around, see above), and real hardware - everything here is Python + RTL simulation.

## 2026-08-14 - BatchNorm folding: standard torch CNNs can enter the pipeline

`Conv2d(bias=False) -> BatchNorm2d -> ReLU` is how nearly every torch CNN is written, and it was the first thing to fail when ResNet pieces were probed the day before. Eight bring-up stages now pass under xsim (`conv_main.py --stage a..h`), 150 tests.

- **The hardware has no BatchNorm concept whatsoever** - `grep -riE "bn|batchnorm|gamma|beta|moving"` over `dataflow.py`, `rtl_export.py` and `runtime.h` returns nothing; the datapath is conv -> +bias -> shift -> activation. Folding host-side is not an optimization, it is the only representation available.
- **The qkeras path was worth copying, but only half of it.** `XConvBN.call_int` quantizes `get_folded_weights()`'s output (`xlayers.py:96-97`) - fold first, quantize second - and that order is now matched. Its *structure* is not copyable: `QConv2DBatchnorm` keeps conv and BN together and re-folds on every call, and brevitas has no equivalent (only `BatchNorm2dToQuantScaleBias` and `merge_bn`). That difference only matters under QAT; with the net in eval mode the running statistics are frozen, so folding once is identical to folding per call, and this backend is PTQ-only.
- **Implementation is a few lines because torch already has the math.** `_fold_batchnorm` (`ptq.py`) calls `torch.nn.utils.fusion.fuse_conv_bn_eval`/`fuse_linear_bn_eval`, which compute `W*gamma/sqrt(var+eps)` and `(b-mean)*gamma/sqrt(var+eps)+beta` and synthesize a bias when the layer had none. Folding the *float* layer before `_quantize_layer` (rather than `merge_bn`-ing a built QuantConv2d) means nothing downstream changes: the fused layer looks like an ordinary conv with a bias, `has_bias` works as before, and `Int32Bias`'s scale is still `input_scale * weight_scale`, so `sim.py:406`'s `acc_frac == bias_frac` assert keeps holding. Folding a `bias=False` QuantConv2d instead would have produced an *unquantized* bias, since `bias_quant` is None there.
- **The eval-mode assert is scoped to layers that are actually followed by a BN**, rather than applied to every model. In train mode a BatchNorm normalizes by the batch's own statistics, so the fold - and the calibration after it - would describe a different model than the one deployed. Models without BN are left alone.
- **The first green run of this proved nothing, and that is the lesson worth keeping.** A freshly constructed `BatchNorm2d` has `running_mean=0, running_var=1, gamma=1, beta=0`, so folding is the **identity**: weights unchanged, bias all zero. `StageH` passed RTL simulation with `Error: 0` while exercising only the plumbing (BN consumed, bias created) and none of the arithmetic. `conv.py::prime_batchnorm` now runs data through in train mode to accumulate real statistics before quantizing, and `test_stage_h_actually_exercises_the_fold` fails if the fold ever degenerates again. **Any test built on a default-initialized normalization layer is vacuous by construction** - the same trap applies to LayerNorm or any affine layer whose defaults are the identity.
- **Per-tensor weight quantization after folding: measured, but not on anything that answers the real question.** Folding multiplies each output channel by its own `gamma_c/sqrt(var_c+eps)`, which widens the cross-channel range, while `Int8WeightPerTensorFixedPoint` gives the whole tensor one scale. On `StageH` the spread of `max|W_c|` came out at **1.08x and 1.04x** max/median - negligible - but that model has random untrained weights, so its channels are statistically identical and the number says nothing about a trained ResNet. Getting a real figure needs a trained checkpoint (no torchvision in this environment). Recorded as an open question rather than a resolved one.
- **Per-channel weight scale is not expressible downstream even if it were wanted:** `ptq.py`'s `quant_weight.scale.item()`, `sim.py`'s scalar `weight_frac`, `XTensor.frac`, and above all `Bundle_t`'s single `i8 ca_shift` - the entire rescale in `runtime.h` is one scalar right-shift per bundle. `Int8WeightPerChannelFixedPoint` exists in brevitas, but using it would need a `Bundle_t`/`runtime.h` ABI change and a matching `pynq_driver.py` change. The qkeras path lives with the same per-tensor limitation (`xlayers.py:71-72`).
- **Verification:** stages a-h under xsim at batch 4, `Bundle n, Error: 0` throughout; `sim.py` vs brevitas differs by exactly 0 values on every stage except `e` (softmax float noise, `2.98e-08`, 0 prediction flips). `pytest` 150 passed / 4 skipped. Nothing under `dataflow.py`, `runtime.h`, `rtl/` or `pynq_driver.py` touched.
- **What ResNet still needs** (measured by pushing real ResNet pieces through, not predicted): a **branching main path** for downsample blocks - one tensor feeding two bundles as main input, which the linear `named_children()` builder cannot express; **strided conv on an even input size** - every strided conv in ResNet18 is rejected, because TF-'same' and torch's symmetric padding disagree by a pixel there; and **`'same'` pooling** plus `AdaptiveAvgPool2d`. Residual add and BN are done.

## 2026-08-14 - strided conv on any input size, via explicit TF-'same' padding

First of the three remaining ResNet gaps (survey: `docs/superpowers/specs/2026-08-14-resnet-remaining-gaps-design.md`). Nine stages now pass under xsim (`conv_main.py --stage a..i`), 156 tests.

- **The engine and torch disagree about where a strided window starts, and only for even input sizes.** The engine convolves at stride 1 with symmetric padding and then keeps pixels from `CSH_SHIFT` (`dataflow.py:44-46`); `torch.nn.Conv2d(padding=k//2, stride=s)` keeps them from 0. For a 3x3 stride-2 conv over an 8-wide axis that is pixels 1,3,5,7 versus 0,2,4,6 - same shape, plausible values, every feature map off by one. Stage c sidestepped it by choosing an odd input size, where the two coincide; that is a workaround, and ResNet's strided convs all sit on even sizes.
- **The fix is to let the float model express TF's asymmetric split, which `Conv2d(padding=)` cannot.** `nn.ZeroPad2d(tf_same_padding(...))` in front of a `padding=0` strided conv lands on exactly the engine's pixels. **Verified numerically against the engine's own path** (`conv2d_same_int` + `_apply_conv_stride`) at `n=8/16/56/224` with `k=3` and `k=7` - including ResNet18's real stem (224/7/2) and stage transitions (56/3/2) - exact match on every one, and pinned by a parametrised test.
- **`XBundle` gained a `pre_pad`, applied before the core.** It exists purely so the float model agrees with the hardware: the engine still receives the **unpadded** tensor and pads internally, so `sim.py`, the adapter and the exporter are all unchanged. The geometry still reports the effective `'same'` padding, because that is what the engine does.
- **The validation is on the exact split, not the total.** A symmetric `(1,1)` pad has the right total for k=3 and is still wrong; `_assert_explicit_pad_matches_engine` compares against `tf_same_padding` per axis and names both. `tf_same_padding` is public for the same reason - hand-computing it is how the off-by-one gets in.
- **Verification:** stages a-i under xsim at batch 4, `Bundle n, Error: 0` throughout; `sim.py` vs brevitas differs by exactly 0 values everywhere except `e` (softmax float noise). `pytest` 156 passed / 4 skipped. Nothing under `dataflow.py`, `runtime.h`, `rtl/` or `pynq_driver.py` touched.

### The remaining ResNet gap is not where it looked

`AdaptiveAvgPool2d` and `'same'` pooling are ordinary Python work. The real blocker is the **branching main path** that downsample blocks need, and the survey found the reason is one line: `runtime.h:249-252` writes a bundle's output in **exactly one consumer's engine tiling** (`pb_out = &bundles[pb->ib_out]`, then `pb_out->cm_p0/cm/x_pad/w/l/p/xp_words`), and the exporter picks `sorted(next_ibs)[0]`. Measured for a 64-channel tensor on `processing_elements=(8,24)`: a 1x1 consumer wants `CM=512, X_PAD=0` while a 3x3 consumer wants `CM=170, X_PAD=6`. The second consumer reads a buffer laid out for the first.

This is why `run/example.py` works: its fan-out is to a *residual add*, which writes an untiled `add_buffers` entry (`runtime.h:244-245`), never two main inputs. **`run/resnet18.py` does have two main consumers** (`x_skip = self.b5(x_skip); x = self.b6(x)` off the same tensor), which suggests that path was never validated end to end - worth confirming before trusting it as a reference.

The fix is to write the output once per distinct consumer tiling. That is `tile_write`/`write_x`, which are **firmware, not fabric** - so it costs a recompile and a matching `pynq_driver.py` change, but no re-synthesis and no new bitstream. Watch the designated-initializer trap the LUT work already paid for: a missing `ib_out` entry defaults to **0**, which reads as "bundle 0" rather than "none".
